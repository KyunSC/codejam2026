## Notes and surprises

- 1.1: Vendor bank details live only in `VendorBankAccount` (versioned; `validTo = null` is live), not on `Vendor`. `BankChangeRequest` keeps `newLast4` because the history CSV has only the last 4 digits. `Document.data` holds uploaded bytes so local runs need no Blob store. Added `Invoice.docType`, `Invoice.normalized` and `Invoice.uploadedById` beyond the plan's list, for stage outputs and the requester rule. `npx tsc` alone fails on `LayoutProps`; use `npm run typecheck` (runs `next typegen` first).
- 1.2: **types.ts appended** with `StepRole`, `Condition`, `Effect`, `PolicyRule` (BUILD_PLAN's shapes). Two additions to `Condition`: `{ any: Condition[] }` because P05 is an OR, and `{ field: 'poPresent' }` because P13 needs "no PO present". P09/P10 compare `totalCad` (one payment per invoice, so payment CAD = invoice CAD). Mapping lives in `src/lib/policy/seed-rules.ts`; `sourceText` is `condition → required`.
- 1.3: `src/lib/audit/chain.ts`. `seq` is not hashed (the database assigns it and can skip numbers on rollback); order comes from `seq`, integrity from the `prevHash` links. Canonical JSON sorts keys at every depth, so jsonb's key reordering on read does not break verification. Decimals hash as their `toJSON` string, the same text Prisma stores.
- 1.4: `npm run db:seed` (= `prisma db seed` → `node scripts/run.mjs prisma/seed.ts`). Wipe is one `TRUNCATE … RESTART IDENTITY CASCADE` over every table; load runs in one transaction. Reference counts match the Tables section on the first run (users 40 … policy rules 13). Dataset timestamps have no zone; stored as written, read as UTC.
- 1.5: **Surprise:** `vendors.csv` already shows V004's *new* account (…9679) although BC-009 was never verified; the history gives only the last 4 digits of replaced accounts. So `VendorBankAccount` now allows null institution/transit/account with a required `last4` (migration `bank_account_last4`): 49 live accounts + 9 last-4-only history versions = 58 rows. The CSV account is the live one (dataset wins); BC-009 is imported `pending`, which is what holds V004. Verified history requests have `verifiedById = null` (the CSV does not say who called back). The two CSVs agree: every change's new last 4 equals the account on file.
- 1.6: History loads 426 invoices, 809 lines, 443 tax rows, 474 approval steps, 415 payments. Payment status `outstanding` (20 cheques) is stored as `sent`, the app's word for a mailed cheque not yet cleared. Invoice status is kept as the CSV writes it. Every history invoice uses one tax code per column, so tax rows are coded from the lines. `invoiceNumberKeys` (item 3.3's number keys) was written here, early, in `src/lib/pipeline/normalize/invoice-number.ts`; 3.3 reuses it.

The seed reads the chain back in `seq` order and fails if it does not verify.

- 3.1: `parseAmount` in `src/lib/pipeline/normalize/amount.ts`. Beyond the plan's rule: currency codes and no-break/thin spaces are stripped; when the comma is the decimal mark, dots are thousands separators (`1.234,56`); a minus may be leading, trailing or parentheses. A thousands separator must sit between groups of three digits, so `12,5` or `1,0145` raise AMOUNT_UNPARSEABLE instead of being read as 125 or 10145 (logged in questions.md).
- 3.2: `parseDate` in `src/lib/pipeline/normalize/date.ts`. An ambiguous numeric date (`03/04/2026`) returns no date, DATE_AMBIGUOUS, and both candidates for the clerk; it does not use the document's language to pick. Two-digit years are DATE_UNPARSEABLE. Weekday names, ordinals (`1st`, `1er`) and abbreviations with dots (`oct.`, `févr.`) are accepted.
- 3.3: `tax-label.ts`, `terms.ts`, `currency.ts` in `src/lib/pipeline/normalize/`; number keys from 1.6. A combined `GST/HST` label is settled by its printed rate (13% → HST13, 5% → GST5), otherwise TAX_LABEL_UNKNOWN. The label's code is kept even when the rate disagrees (`HST 5%` → HST13 at 0.05): the tax checks judge it. Unrecognised terms keep the raw text with null days (no ParseIssue code exists for terms). A bare `$` or a label naming both currencies gives null currency.
- 3.4: `FxTable` and `toCad` in `src/lib/pipeline/normalize/fx.ts`. All 426 history invoices reproduce their `fx_rate_to_cad` and `total_cad` (rate for the invoice date, CAD rounded half-up to the cent). Past 2026-11-02 the last row is used with `fallback: true` (FX_RATE_FALLBACK). A date before the first row has no rate (null) rather than borrowing a later one.
- 3.5: `inspectDocument` in `src/lib/pipeline/inspect.ts`; PDF.js wrapper in `src/lib/pipeline/pdf.ts`. Added `pdfjs-dist@6.4.299` and `sharp@0.35.5` (already installed via Next; now direct), both pinned. `unpdf` was tried first and fails on Node 20 (needs `Iterator` helpers); pdfjs-dist 6 needs `Promise.withResolvers` (Node 22+), so `pdf.ts` polyfills it. PDF.js refuses a Node `Buffer` (it says so in an error that looked like corruption): always pass a plain `Uint8Array`. `next.config.ts` gains `serverExternalPackages: ["pdfjs-dist"]`. Named problems: empty, unsupported_type, encrypted, corrupt, blank_image. All 41 unsealed files open: 40 one-page PDFs with text layers, 1 PNG. Test PDFs (incl. a password-protected one, RC4 rev 2) are built in memory by `src/lib/pipeline/__tests__/pdf-builder.ts`.
- 3.6: `computeEvidence` in `src/lib/pipeline/evidence.ts`. Text fields match the text layer as letters+digits only with digit boundaries; numbers match by value against every 1–4-word numeric run in the text (removing all spaces made neighbouring columns run together: `10 150.00 1 500,00`). When arithmetic closes, all numbers are confirmed even if reformatted. A scan's text fields with no second read get no evidence entry (nothing could check them). Review rule: required fields (vendor name, invoice number, invoice date, total) that are anything but confirmed, plus any uncertain/unreadable field anywhere. See questions.md.
- 3.7: `normalize` / `normalizeDetailed` in `src/lib/pipeline/normalize/index.ts` (the detailed form also returns needsReview, reviewFields, arithmetic for intake). Unparseable values become null plus a ParseIssue; a tax whose amount does not parse is dropped (its issue stays). Credit notes printed positive are negated (money fields only, not quantities); evidence still runs on the printed values. FX and vendor are left to Resolution. Fixed a 3.6 bug found here: a label ending in a digit (`TPS 5 %`) was rejected because, with spaces stripped, it ran into the next amount; the digit boundary now looks at separators in the original text, and numbers that parse match by value only.
