  - `src/lib/preferences.ts`: TABS (with href/match/action, moved from `App.tsx`'s inline list; App still has its own copy until item 6), DASHBOARD_TILES and DASHBOARD_CARDS (permissions copied from `loadDashboard`), SECTIONS, TABLES, `preferencesSchema`, `DEFAULT_PREFERENCES`, `resolvePreferences`, `resetPage`, `migratePreferences`.

  - **Added beyond the plan: `sanitizePreferences(doc)`.** Reading is lenient: a stored document with an id or value the app no longer has would fail the strict schema, so `migratePreferences` sanitizes it (drops only the bad parts). Its result always passes `preferencesSchema`, so the app can edit and save it back without a 400.
  - **Schema strictness (the plan said both "stripped" and "rejected"):** unknown top-level keys are dropped; unknown ids or values inside lists and tables are refused with the field's path (e.g. `tables.invoices.pageSize`, `tabs.0.id`). A `filter` on a table with no filters, or a `pageSize` on an unpaged table, is refused as an unknown key. Duplicate ids are dropped, first wins; lists capped at 30.
  - **Locked items keep their default position**, as plan 1.2 says ("can't be dragged out of place"), unlike the prototype, where the Dashboard tab could move. So the Payments `totals` section can be hidden but not moved, since `list` is locked after it.

- [x] 4. Provider + appearance: src/web/preferences.tsx, data-* on <html>, globals.css, no-flash script in index.html.
  - `src/web/preferences.tsx`: `PreferencesProvider` (in `main.tsx`, inside `SessionProvider`) and `usePreferences()` → `{ prefs, stored, loading, update, undo, canUndo, resetPage, resetAll, saveState, retry }`. Changes resolve locally at once; the full stored document is PUT 400 ms after the last change; on failure `saveState` is `error` and `retry()` re-sends.
  - **Keyed by user id** (an inner `UserPreferences` with `key={user_id}`): signing in as someone else starts from fresh state (their cache, empty undo stack, no pending save). Resetting state in an effect fails the `react-hooks/set-state-in-effect` lint rule; the key avoids it.
  - Cache: `brim:prefs:<user_id>` holds the stored document (sanitized on read, so a stale cache can't cause a 400) and `brim:prefs:last` holds the appearance for `index.html`'s inline script, which sets the `data-*` attributes before the bundle loads. Signing out removes `brim:prefs:last`, so the login page shows the defaults. All localStorage access is in try/catch.
  - **Split from the plan:** the zod schema moved to `src/lib/preferences.schema.ts` (server and check script only). Importing it through `preferences.ts` pulled zod into the browser bundle: 340 kB → 434 kB. After the split: 349 kB, no zod in the bundle.
  - `globals.css`: dark tokens now under `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) }` and again under `:root[data-theme="dark"]` (two identical blocks with a comment; plain CSS can't share one block between a media query and an attribute selector). `--accent: var(--red)` used for the `.btn--solid` shadow, `.link` underline, `.tabs` and `.wtabs` current markers; semantic reds unchanged. `body` font-size `16px` → `1rem` (same size by default) so `data-text-size="large"` (`html` 112.5%) scales it with the Tailwind rem sizes. Compact rules are unlayered so they beat utilities; card body keeps its 1.25rem sides because `Table` uses `-mx-5`.
  - Same look by default: no CSS targets the default attribute values (`comfortable`, `red`, `normal`), and `--accent` equals `--red`.
  - Verified: typecheck, lint, build; on port 3100 the served page carries the inline script, `/src/web/preferences.tsx` loads (200), the API still refuses `theme: neon`; the built CSS has the guarded dark selectors and the accent/density rules. **Not verified in a browser:** the actual theme switch, no-flash on reload, and compact/large looks.
